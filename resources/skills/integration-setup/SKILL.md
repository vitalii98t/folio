# Integration Setup (Нова інтеграція)

## Філософія
Folio не має готового списку "підтримуваних сервісів". Будь-який сервіс з API + документацією може стати інтеграцією. Твоя задача — провести юзера через діалог, у якому ти **сам розбереш документацію** і налаштуєш правильний syncPrompt, який потім крутитиметься у фоні.

**КРИТИЧНО:** не пропонуй конкретні сервіси за назвою (Monobank, Stripe, Privat). Запитуй generic'ом — юзер сам скаже, що йому треба.

## Воркфлоу

### Крок 1. Запит документації
Перше повідомлення — generic:
> "Якщо сервіс має API — надішліть документацію (файл, посилання, або просто опишіть). Я з нею розберусь."

Прийми у вигляді:
- URL до OpenAPI/Swagger/REST-doc сторінки
- PDF/Markdown файл
- Текстовий опис ендпойнтів від юзера

### Крок 2. Аналіз документації
Прочитай і витягни **обовʼязковий мінімум**:
- Спосіб авторизації (API-key in header / Bearer token / OAuth / Basic Auth)
- Базовий URL
- Ендпойнт для отримання операцій / транзакцій
- Параметри запиту (як фільтрувати по даті — `from`/`to`, `since`, тощо)
- Структура відповіді (де лежить масив операцій, як називаються поля сума/дата/опис)

Підсумуй юзеру коротко: "Я розібрався: авторизація через X, операції тягнемо з ендпойнту Y, фільтрація по даті — параметр Z." Це дає юзеру шанс виправити, якщо ти зрозумів неправильно.

### Крок 3. Запит конфігурації
Запитай юзера три речі (компактно, в одному повідомленні):
1. **На який рахунок Finmap** зачислятимуться операції? (виклич `mcp__finmap__get_accounts` для списку)
2. **З якої дати починаємо синхронізацію?** ("Тільки нові з сьогодні", "За весь минулий місяць", "За весь минулий рік")
3. **API-key/token сервісу.** Юзер дасть.

### Крок 4. Перша синхронізація — НА ОЧАХ ЮЗЕРА
**Це НЕ автомат.** Юзер має побачити що відбувається перед тим як ми це збережемо як автоматизацію.

1. Виклич `mcp__finmap__http_request` до сервісу — отримай операції за заданий період.
2. Покажи юзеру: "Знайдено N операцій. Ось перші 5: ..."
3. Запитай: "Створити їх у Finmap?" — якщо так, по одній виклич `mcp__finmap__create_operation` (через підтвердження юзера або в режимі mass-import — див. `mass-import` skill).

**ОБОВʼЯЗКОВО** для кожної операції:
- Поле `externalId` = `{serviceName}_{originalId}` — це для майбутньої дедуплікації.
- Категорія, контрагент, тег — за дефолтами або як юзер скаже.

### Крок 5. Збереження інтеграції
Якщо перша синхронізація успішна — виклич `mcp__finmap__save_integration` з:

- `serviceName` — коротка назва (наприклад, "monobank-personal", без емоджі і пробілів — використовується у `externalId`)
- `serviceApiKey` — ключ юзера
- `finmapAccountId` — ID рахунку
- `enabled: true`
- `syncIntervalMin` — за замовчуванням 30, спитай юзера "як часто перевіряти?"
- `syncPrompt` — **детальна інструкція для майбутніх автозапусків.** Шаблон у [reference/sync-prompt-template.md](reference/sync-prompt-template.md).

Підтверди юзеру: "Інтеграція **{serviceName}** збережена. Наступний автоматичний запуск через {N} хвилин."

### Крок 6. Перевір що НЕ створив дублікат
Перед `save_integration` виклич `mcp__finmap__list_integrations` і подивись, чи не існує вже інтеграція з тим самим `serviceName`. Якщо існує — НЕ створюй нову, а скажи юзеру "Така інтеграція вже є — використай команду 'зміни інтеграцію X' для оновлення" (це активує `integration-modify` скіл).

## syncPrompt — найважливіший артефакт

Це інструкція, яку SyncScheduler потім крутитиме автоматично кожні N хвилин **без UI і юзера**. У ній має бути все — URL, headers, як парсити, як мапити в Finmap. Шаблон і приклади — у [reference/sync-prompt-template.md](reference/sync-prompt-template.md).

**Правило:** якщо в syncPrompt відсутнє щось критичне (наприклад, не зазначено куди поле "amount" з банку мапити у Finmap-операції) — автосинк зламається через тиждень коли юзер вже забуде деталі. Перевір syncPrompt сам перед save_integration.
